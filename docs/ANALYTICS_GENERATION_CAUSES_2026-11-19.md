# Analyticsがない・空・電池情報がない場合の原因調査

2026-11-19の継続調査。[最初の調査](ANALYTICS_GENERATION_2026-11-19.md)と同じ
Apple配布のiPhone14,4 / 27.2 (24B119) を静的解析し、手元の実機・保存ファイルと照合した。
目的は、生成・集計・保存・取得を分け、現象を単に「OSの気分」と扱わないこと。
以下のアドレスはこのビルド専用で、全OS版・全モデルの保証ではない。

## 原因を区別する表

| 現象 | 確認できた仕組み | まだ区別が必要なこと |
| --- | --- | --- |
| ファイルが生成されない | 通常Sinkの共有設定ゲート、日次処理の再始動中・別処理進行中のスキップ、作成・書き込み失敗の経路 | その実機で実際にどの分岐に入ったか。タイマー1回のスキップは、その日全体の欠落を意味しない |
| ファイルが見つからない | ロック中の診断サービスはPasswordProtectedで拒否する。OSにはRetiredへの移動・削除もある | 未生成なのか、別の置き場なのか、生成後に削除されたのか、読めないだけなのか |
| 内容がほぼないが形式は完結 | 書き出し処理は保存された集計を列挙し、メタデータとEOFを出力する。0イベントでも通る経路がある | 実機由来の0イベントの完結ファイルは今回未採取。状態未蓄積・設定変更等の実行履歴が必要 |
| 短いが電池情報は正常 | 短いファイルでも必要な電池行があれば成立する | 行数を測定回数・不完全さの代用にしない |
| 形式は完結しているが電池情報がない | 週次など別期間の集計、Census、バッテリーを持たないOS、電池イベントの入力不足を区別できる | 当該ファイルの期間・イベント種別と生成時の入力状態 |
| 電池行はあるが必要値がnull等 | 入力フィールド不足・別の電池イベント等を、電池行自体の不在と区別する必要がある | 値が取得できなかったのか、取得済み値が記録されなかったのか |
| 0バイト・途中のJSON | 正常な完結ファイルとは違う。書き出し・コピー途中、失敗等の切り分けが必要 | OS上のサイズと取得後サイズ、再取得時のハッシュ、JSON/EOF、OS側の書き込みエラー |

この表は原因の候補を観測で区別するためのもの。静的に存在する分岐を、全て実機で再現済みとは扱わない。

## 1. 電池情報の収集とAnalyticsファイル生成は別の時計

PowerlogLiteOperatorsの `+[PLBatteryAgent defaults]`（`0x29fca80d0`）が返す
定数辞書（`0x2d3dae4d8`）を読み取り、次の初期値を確認した。
数値オブジェクトのペイロードはIEEE 754のdoubleとして格納されている。

| 設定キー | 初期値 | 秒としての長さ |
| --- | ---: | --- |
| AggdTimerBatteryConfig | 21,600 | 6時間 |
| RateLimiterBatteryConfig | 86,400 | 24時間 |
| GasGaugeLogInterval | 300 | 5分 |
| RateLimiterBatterySample | 900 | 15分 |
| xFlagsRetryTimerInterval | 300 | 5分 |

**同じ処理の間隔ではない。これらを「Analyticsは6時間／24時間おきに必ず生成する」という意味にしない。**
RateLimiterBatteryConfigの値は確認したが、その全適用経路と実機での有効値の確定は残る。
設定の上書き、起動状態、タイマーの起点・実行遅延によって実際の時刻は変わり得る。

6時間タイマーは参照先も追えた。

1. `-[PLBatteryAgent init]` の初期化ブロック `0x29fca8e58` において、
   `0x29fca97f0` でAggdTimerBatteryConfigを指定する。
2. `0x2a00adea0` のセレクタは `defaultDoubleForKey:`。返されたdoubleを保持する。
3. `0x29fca989c` は
   `initWithFireDate:withInterval:withTolerance:repeats:withUserInfo:withQueue:withBlock:` の呼び出し。
   直前にintervalへ値を渡し、repeats=1を設定している。
4. `setPeriodicAggdTimer:` でタイマーを保持する。

初回fireDateも、同じ値を渡した `monotonicDateWithTimeIntervalSinceNow:` で作る
（セレクタstub `0x2a00a9b50`）。このタイマーはAnalyticsのUTC日付境界とは別の起点を持つ。
ただし通知や直接入力の別経路があるので、「起動後は必ず6時間待つ」という意味ではない。

別に `com.apple.powerlogd.PLBatteryAgent.pushConfigToAggd` 通知への登録があり、
`_pushConfigToAggd`（`0x29fcaada0`）から `aggdTimerFired` へ進む経路もある。
通知の送り元・全発火条件はこの時点では未確定。

### 保持している電池データがないとイベントを出さない経路

`-[PLBatteryAgent aggdTimerFired]`（`0x29fcba6f0`）:

- `0x29fcba834` で `lastBatteryConfigEntry` を取得する。
- `0x29fcba844` でnilなら、そのまま終了経路 `0x29fcba93c` へ進む。
- nilでなければ `logBatteryConfigToAggd:` と
  `logBatteryConfigToCA:forBatteryPack:`（ここではBatteryPackID=255）を呼ぶ。
- CA送信側は `_AnalyticsSendEventLazy` へイベントを渡す。

従って、この経路は送信のたびにその場で電池を読み直しているわけではない。
保持データ未取得なら、そのタイマーからの電池イベントは発生しない。
ただし `logEventNoneBatteryConfigWithRawData:` から直接CAへ送る別経路も存在するため、
「lastBatteryConfigEntryがnilならOS全体で一切送れない」と一般化してはいけない。
再起動後に保持データがどう復元されるかも未確定。

この分離によって、「今日作られたファイルなら電池値も今日取得した値」とは限らないことが分かる。
参考として、91ファイル中の175電池行の `last_value_UpdateTime` をUNIX秒と仮定して計算すると、
ヘッダー時刻より24時間超古いものが13行、最大差は約64時間あった。
これはフィールドの時刻解釈に基づく参考値で、Appleによるフィールド仕様の確認結果ではない。
行は同一ファイル・同一端末内でも複数あるため、175台や175日分の独立標本とは扱わない。

## 2. 集計期間とoutputs.sinkは別の指定

前回調査で未確定だった `sink: Never` を、集計期間の意味と混同しない。
集計期間の選択関数 `0x10001606c` を追加で追った。

```text
collectionCadence が指定されていれば、それを解釈
なければ aggPeriod を解釈
両方なければ 0（Daily）
```

`0x1000401a4` の比較処理はDaily=0、Weekly=1、Monthly=2、Quarterly=3を返す。
従って、バッテリー3定義で両指定が省略されていることと、実ファイルでDailyになることが対応する。
`outputs.sink` だけを見て、このレポートは週次／日次、と判定してはいけない。

27.2通常設定の14,351 transformについて、aggPeriodの明示指定は次のとおりだった。

| aggPeriod | transform数 |
| --- | ---: |
| 省略 | 13,289 |
| Daily | 989 |
| Weekly | 62 |
| Monthly | 8 |
| Quarterly | 1 |
| Session | 2 |

この集計は設定のキーを数えたもので、全transformの有効状態を表していない。
collectionCadenceによる優先指定やSamplingなどの条件を除いた、ファイル生成数の予測でもない。
Weekly用の集計を含むファイルに、日次用の電池行が必ず入るとは言えない。

### 月曜日に集中する対象外ファイル

PCの対象外履歴に残る11ファイル中、10ファイルの日付が月曜日だった。
一部は約24〜32KB、Watch側では複数週とも2,429 bytesという履歴もある。
これは週次レポートの可能性を調べる具体的な手掛かりだが、**原本のaggregationPeriodはまだ未確認**。
`.000` という連番や曜日だけで週次と確定してはいけない。
診断サービスがロックによる読み取り拒否を返したため、原本の回収は解除後の確認事項とした。

## 3. 共有をオフにした場合にも別のログがあり得る理由

通常用DefaultSinkとOptOutSinkの仮想関数テーブルをMach-OのfixupとRTTIから照合した。
共有設定の判定は、同じメソッドを全Sinkが使っているわけではない。

| 役割 | DefaultSink | OptOutSink |
| --- | --- | --- |
| vtable address point | `0x1001b1bb8` | `0x1001b4818` |
| 書き出し許可を判断するslot | `0x1000d2484` | `0x1000ab5f0` |
| 許可処理 | 通常のoptInApple等の確認へ進む | `mov w0, #1; ret` |
| ファイル名側の関数 | `0x1000d1d54` | `0x1000ab5bc` |

OptOut側のファイル名関数は `Analytics-Census` を返す。
さらに `0x1000ab5f8` 以降には `kOSALogOptionOptInOverride` を設定する処理がある。
前回確認したOptOut設定はCensusのみ、Weekly、端末ごとの安定乱数bucketが10未満という条件を持つ。

これで、通常の共有設定ゲートを見ただけでは説明できなかった「オフでも別種のログがあり得る」経路を区別できる。
ただし、全てのオフ端末にCensusが生成される、通常の電池ログもオフで生成される、とは言えない。
安定乱数の抽出条件を、毎回その場の気まぐれで生成する仕組みと解釈しない。
実機の有効設定がIPSW同梱設定から更新されている可能性も残る。

Appleの[共有設定の説明](https://support.apple.com/en-us/108971)は設定場所を案内しているが、
全内部レポートの生成条件を公開しているわけではない。
上記の内部経路は、この調査で解析したAppleバイナリを根拠とする。

## 4. 「0イベント」と「0バイト」は別

analyticsdの書き出しブロック `0x1000d0f48` は、おおむね次の順に動く。

1. `0x1000d0f94` でメタデータをシリアライズして書く。
2. `0x1000d1030` で永続化されたtransform状態を列挙し、各メッセージを書く。
3. メッセージ数に関する確認はあるが、0件だから即座にファイル全体を破棄する分岐にはなっていない。
4. `0x1000d107c` からEOFオブジェクトを作り、`0x1000d108c` で書く。

EOFは `{"_marker":"<end-of-file>"}`。
従って、メタデータとEOFがある短いファイルと、途中までしか書けていないファイルは区別できる。
なおEOFがあっても途中のJSONが壊れている可能性はあるため、全行のJSONと終端の位置も確認する。
古いOS・別レポート形式について、EOFがないだけで破損と断定してはいけない。
この経路で正常完了したファイルが0バイトになる、という説明は成立しない。

`0x1000d1118` の行書き込み処理ではJSON本文と改行をwriteする。
別途、ログ作成失敗・書き込み失敗の処理も存在する。
しかし、今回0バイトの実ファイルやOS上の書き込み失敗を採取できたわけではない。
0バイトの原因をディスク不足・OSのクラッシュ・PCのコピー失敗のどれかへ決めつけない。

## 5. 日次処理のスキップと「読めなかっただけ」

日次処理の入口 `0x100072c40` には、再始動処理中や既存rolloverの進行中に
その呼び出しをスキップする分岐がある（`0x100072cd0`、`0x100072d10`付近）。
後の再試行・起動時の期限超過処理も考える必要があり、スキップ1回を「丸1日生成されない」と扱わない。

実際のiPadでは、CoreDevice経由で今日のAnalyticsをコピーできた一方、別時点の診断サービス呼び出しは
`PasswordProtected`で拒否された。保持済み・公開範囲の異なるサービスの結果を同一視しない。
また、この時のpymobiledevice3 CLIはstderrへエラーを書きながら終了コード0を返した。
終了コード0・一覧0件だけで「Analyticsが生成されていない」と判断してはいけない。
製品のCollectorはstderrも確認する仕組みを持っている。

### Retired内には7日を基準に削除する処理がある

OSAnalyticsの `+[OSALog cleanupRetired:]`（`0x1b1df1a1c`）はRetiredディレクトリを走査する。
ブロック `0x1b1df1b5c` はファイル属性の `fileModificationDate` を取得し、
`timeIntervalSinceNow` の絶対値と、`0x1b1e14968` のdouble定数604,800秒を比較する。
差が7日を超えると `_OSASafeRemoveFileAtURL` の経路へ進む。

これで「生成されていない」と「以前生成されたがRetiredの整理で消えた」を区別すべき理由も具体化できる。
これはこのクリーンアップが実行された場合の条件。生成から厳密に7日後の削除保証や、
OSの全ログの保存期間が一律7日という意味ではない。他の保存場所・削除条件・実行時刻も区別する。

OSのDBマイグレーションにはsessionの秒／マイクロ秒補正（V16）などがあるが、
比較した27.0.1と27.2の両方に対応文字列がある。
この存在だけを27.2で新たに起きた欠測の原因としない。

## 6. 今回の実測と、原因確定に残る観測

- 新たに直接コピーしたiPadの当日ファイル: 98,676 bytes、163行、Dailyのイベント160行、
  完全な電池行2件、メタデータとEOFあり、JSONエラーなし。OSは27.0.1。
- 既存90件と合わせた91件は、全てメタデータ・EOFがあり、電池の必須値も揃っていた。
- iPadのアプリ内に残る別の失敗原本1件は、約2.1MB・3,703行のApple TVOSのログだった。
  EOFまであり電池行がない。この例を「iPad自身の電池イベントが欠落した」と扱わない。
- Mac自身のOS統合ログでは、日次rollover開始、ファイルへの3,471メッセージ書き出し成功、
  完了という順序を確認した。Macでの観測であり、iPhoneの失敗再現ではない。
- 0バイトの実ファイル、iPhone/iPad由来の完結した日次レポートで電池行だけがない原本、
  対象外履歴に残る月曜日の原本は、この時点では未採取。

次の異常時に必要なのは「短かった」という記憶だけではなく、次の対応関係。

| 記録する観測 | 区別できること |
| --- | --- |
| OS上の一覧の成功・失敗、置き場、サイズ | 未生成と読み取り拒否・移動・削除 |
| 取得前後のサイズ・mtime、再取得ハッシュ | 書き込み途中・コピー途中・安定した原本 |
| OSヘッダー、メタデータ、全行JSON、EOF | 完結した別種レポートと途中のファイル |
| aggregationPeriod、電池イベント名、必須キーの有無・型 | 週次等の別期間、電池行なし、値だけ不足 |
| 同時間帯のanalyticsd/PowerlogのOS統合ログ | 実際に実行された許可・入力・集計・書き込みの分岐 |

問題の原本が得られるまでは、コード上で特定した条件と、実際にその条件が成立したという証明を分ける。

## 読み取り専用の分類ツール

```sh
python3 scripts/research/classify-analytics-report.py /path/to/Analytics.ips.ca.synced
python3 Tests/AnalyticsReportResearchTests.py
```

ファイル名・パス・個体ID・利用履歴・バッテリーの数値は出力しない。
0バイト、完結した少量データ、電池行なし、必須値不足、途中の形式、読み取り中の変更を分ける。
64MiB/ファイル、4MiB/行の上限があり、ネットワーク通信や端末設定の変更はしない。
研究用の構造判定で、製品パーサーの全仕様や全OS形式の互換性を表すものではない。
10ケースの合成試験と、92件の保存ファイルで分類動作を確認した。
製品のパーサー・収集条件はこの調査では変更していない。
