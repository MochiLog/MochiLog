## 前段から変わった結論

**低電圧滞在の単位は全機種共通ではなかった。** 前段で確認した
BatteryAlgorithmsの「値×0.01秒」「先頭18個が3V未満」は、その利用側の形式に対する定義。
ゲージの生成側では、同じ27要素でも1秒単位のもの、電圧境界が異なるものがある。
108バイトという長さだけでは換算できない。前段の説明を全機種へ適用してはいけない。

新たに確定したのは、高残量域の10区分と時間単位、3種類の低電圧区分、
SlowChargingReasonの16を立てる経路、累積値の不揮発保存、iPadのセル切断カウンターの保持方法。
機種・ファームウェア版が一致する範囲と、一致していない範囲を以下で分ける。

## 1. TimeAtHighSocの10区分

### 単位と並び

調査した10区分のSMC出力は**整数の時間（hours）**。
ゲージ内の秒カウンターをSMCが3,600で割ってからBLTPへ置く。
AnalyticsのLastを日ごとに足してはいけない。

| bin | 残量域（公称） | 温度域（公称°C） |
| --- | --- | --- |
| 0 | 95%以上 | 25未満 |
| 1 | 95%以上 | 25以上30未満 |
| 2 | 95%以上 | 30以上35未満 |
| 3 | 95%以上 | 35以上40未満 |
| 4 | 95%以上 | 40以上 |
| 5 | 90%超95%未満 | 25未満 |
| 6 | 90%超95%未満 | 25以上30未満 |
| 7 | 90%超95%未満 | 30以上35未満 |
| 8 | 90%超95%未満 | 35以上40未満 |
| 9 | 90%超95%未満 | 40以上 |

端点の正確な定義は整数比較。SOCはQ29、温度はKelvin Q17で、
90%側の比較は`>0x1ccccccc`、95%側の境界は`0x1e666666`。
温度の上限配列は`[0x2544ccd, 0x25e4ccd, 0x2684ccd, 0x2724ccd, 0x7fffffff]`で厳密な`<`。
表の公称値を浮動小数点に変換して再比較するより、台帳の整数を使う方が境界を保存できる。
先頭温度区分は「0〜25°C」に限定されていない。

ゲージのselector 6は90〜95%側、7は95%以上側。
SMCはselector 7を先頭5個、6を後半5個へ配置するため、通信順をそのままbin順にしない。
Veridianの増分処理は`0xe4e0`、Volchok X3357は`0x16146`、Watchは`0x1602e`。
後二者の低電力経路には300秒単位の加算もある。秒数の累積であって1秒ごとの観測列ではない。

旧SMCの読出しは`0x5ff4–0x60d4`、割り算の補助関数は`0x566ac`。
先頭5個には割り算後の下位16ビットだけを残す処理がある。
65,536時間の境界で値が小さくなり得るため、全ての減少を日次リセットや電池交換にしない。
この16ビット処理も、未照合の全ゲージへ一般化しない。

### Appleの重み付き使用

BatteryAlgorithmsの`convertTeqIntoScalar`（iPhone側`0x25a0747d4`）は
signed int32の各値に機種モデルの係数を掛け、呼出元の除数で割る。
ACAM経路の除数は100。48設定に15通りの係数があり、比較したiPhone・Watch画像では48設定が一致した。
既定設定の一例は`[10,16,28,48,82,8,11,20,35,60]`。
コンストラクター直後の別配列はモデル設定で上書きされるため、既定値と取り違えない。

これは温度・残量に重みを付けたモデル用の等価時間で、通常の高残量合計時間ではない。
全利用者に1種類の係数を使うことも、独自の劣化率%に直すこともできない。

### 実ログに結び付けられる範囲

保存済みWatchログのゲージ版は209400036で、今回のWatch配布物と一致した。
一方、保存済みiPhoneログは209200029で、配布物の209200028と一致しなかった。
同機種の27.0.1 / 24A446、27.2 / 24B119、27.2.1 / 24B156のFirmwareMapも照合したが、
いずれも同じ209200028のペイロードだった。
29の実体を得ていないので、28の区分が29でも同じと確定することはできない。
iPadのBLTPは4カウンターであり、10区分表は適用しない。

さらにiPadのSMC読出しを追うと、4個はゲージから届いた独立した秒カウンターではなかった。
TIドライバーの更新関数`0x8a8c`内、版0x610 / 0x611等の分岐`0x8e4c–0x8f34`は、
TotalOperatingTimeと同じ元のbig-endian u16（オブジェクト+0x79）に、
続く4個のu8（+0x7b…+0x7e）をそれぞれ掛け、100で整数除算してBLTPへ置く。
式は`floor(元の稼働時間 × 区分別の割合 / 100)`。
保存済みiPadログの版1552は0x610に対応する。
従って、区分の百分率化・整数化ですでに精度が落ちており、細かい日次差分を復元できない。
ゲージがこの4個の割合を作る残量・温度の境界は、SMCが受け取るバイト列には含まれない。

## 2. LowVoltageResidencyCountersの27区分

並びは`電圧index × 9 + 温度index × 3 + 絶対電流index`。
各軸の4境界から3区分を作る。公称値は次の通り。

| ゲージ | 電圧境界 V | 温度境界 °C | 絶対電流境界 A | 1カウント |
| --- | --- | --- | --- | --- |
| Veridian X1861 / 109060052 | 0, 2.7, 2.85, 3.0 | 有効Kelvin下限, 30, 40, 番兵上限 | 0, 0.1, 2, 20 | **1秒** |
| Volchok X3357 / 209200028 | 0, 2.7, 3.0, 3.2 | 有効Kelvin下限, 20, 30, 番兵上限 | 0, 0.25, 1, 100 | **0.01秒** |
| Volchok X3528 / 209400036 | 0, 2.5, 3.0, 3.2 | 有効Kelvin下限, 25, 35, 番兵上限 | 0, 約0.010002, 約0.099998, 20 | **1秒** |

全て下限を含み上限を含まない整数比較。温度の0は0°CではなくKelvin Q17の0。
高温側の`0x7fffffff`も実用的な温度値ではなく番兵。Q17の丸め差は台帳に保持した。
電流は絶対値なので、充電／放電の区別はこの軸から復元できない。

旧ゲージの1秒増分処理、Watchの同処理、新ゲージの100倍積算処理を照合した。
X3357の`0x16a9a`は27個の短期カウンターから、観測回数×100をu32へ加える。
別経路`0x16934`はミリ秒を10で割って切り上げる。
SMC側の低電圧分数換算も、機能ビット23で60または6,000を使い分けており整合する。

したがって、前段の「先頭18個が3V未満」はX3357・Watchのこの電圧表には対応するが、
Veridianでは3番目の電圧群も3V未満なので対応しない。
汎用BatteryAlgorithmsの関数が存在するだけで、旧ゲージにその関数が適用されるとは証明できない。
Appleの不具合だと判断する根拠にもならない。

Analytics側で各binを2有効数字に丸める制約は変わらない。
正しい単位が分かっても、丸めで失われた短い日次増分は復元できない。
負数、全ビット1、飽和値は通常の滞在時間として表示しない。

## 3. 累積値の保存と形式更新

「日次ファイルにあるから日次リセット」ではないことを、保存側まで確認した。

| ゲージ | 起動時の復元 | 保存処理 |
| --- | --- | --- |
| Veridian | `0xbf84`。不揮発領域0x20000 / 0x21000を検査し、有効な4KiBをRAMへ復元 | `0xc0b8`。汚れ状態・期限・強制保存に応じ、交互の領域へ保存 |
| Volchok X3357 | `0x15ea6`。0x8000 / 0x9000を検査して復元 | `0x15f48`。同様に交互保存 |

有効な保存内容がなければ別の既定値初期化へ進む。
通常起動の復元と、初期化・保存破損・形式移行は別経路。
直前の未保存分まで電源断に耐えることや、工場／修理の全操作に対する保持を保証するものではない。

X3357の`0x16a58`には旧LVR値を100倍する形式移行がある。
初期化経路`0x15c8c`は形式マーカー0x4d53を保持する。
値が100倍になっても、突然100倍の低電圧時間が発生したとは限らない。
新旧のファームウェアと形式を記録せず、単純差分を取る設計は不可。

## 4. SlowChargingReason = 16

旧SMCの`0x18494–0x184c0`は、`0x1a23c`で求めた電流制限が基準電流を下回ると
CHSWのbit 4（数値16）を立てる。
この制限の係数はB1WI。B1TIを使う別経路がbit 3（8）で、温度制御側と対応する。

新SMCでも、誘導充電側の処理`0x48218–0x48264`が
`IND: CHG: request charge rate`を記録してB1WIへ係数を書き、
`0x3bd74`側に`IND: CHG: clear charge rate`と制限解除がある。
従って16には**無線／誘導充電制御からの電流制限**という根拠がある。
「充電器が弱い」「温度が高い」「故障」といった具体的な原因を16だけで付け足さない。
制限を要求した制御器の内部判断全体や、CHSWの全ビット表まで解読したという意味ではない。

## 5. iPadのBatteryCellDisconnectCount

対象はiPad16,6のSMC `H16_4-7372.42.1.j72x.REL`、SHA-256
`69ec0cd4f9d80bc3876498f3e6364a8285adea57b555161da3b730a621cdb904`。

- SMCキー`bcc0`は1バイト`ui8 `。ハンドラー`0x23e30`がRAM 0xaa52bを返す。
- カーネルの同名プロパティにはBCDCとbcc0の別プラットフォーム記述子がある。
  記述子はプロパティ名の**後ろ**にあり、直前のbfM0を誤って対応させない。
- TIドライバーのこの版では、仮想関数0x480 / 0x488 / 0x490が非対応値0x8000000bを返す。
  その場合はSMCの保存項目`CELD`（識別子7）へフォールバックする。
- `0x28eec–0x28f34`は保存済み値を読み、255未満なら1増やし、保存してRAMへ戻す。
  **255で飽和**し、USB接続ごとに加算する経路ではない。
  読出し失敗時に1を初期値として保存する分岐もあり、復元失敗と正常な加算を区別する必要がある。
- `0x265f8–0x26888`には電流値の比較、短期状態の観測カウンター、判定フラグを経た加算条件がある。
  抽出した命令だけで、全機種共通の物理的断線条件や秒数を命名しない。

Apple公開PowerManagementの
[checkCellDisconnectCount](https://github.com/apple-oss-distributions/PowerManagement/blob/d415e45501842834a280930c3eed9186544a67f0/pmconfigd/BatteryTimeRemaining.m#L3123)
もSMC対応・機能対応を確認した上でヘルス判定へ用いる。
公開コードの閾値10を、今回の全端末へ「故障確定」の線として表示しない。
修理回数、実際にコネクターが外れた回数、当日の回数ではなく、まず内部判定の累積値として扱う。

## 6. Watchの時間帯データと温度分布

Watch固有のPowerlog、IOKit、powerd、BatteryAlgorithmsも追加照合した。
27.2.1 / 24S132に加え、実ログと同じ**27.2 / 24S118**のシステム本体も取得した。
同版の生成側でも、既定900秒、HHmmの区間終了ラベル、最後の保存済み温度、
Temperature÷100、欠損値127 / 1000という構造を確認した。
WatchではChargerVoltageのメトリックも実際に構築する。前段のiPhone側との差を解消した。

[同版比較台帳](research/watch-exact-comparison-27.2.json)に抽出画像のハッシュと照合範囲を保存した。
6つの生成関数はアドレス指定命令以外の変更がなく、参照する45定数・配列と103のObjC呼出しも一致。
移動した参照アドレスを無視しただけではなく、双方のキャッシュから実際の文字列・配列を読み直した。
既定設定辞書のIntervalDuration=900.0も同版から取得した。
powerd全体はバイト単位で一致。LVRの2計算関数と倍率・マスク、ACAMの48組の重みも同版と一致した。

powerdの`0x10001be54`はBHT0〜BHTBを読み、OS保管庫へ加えた後SMC行をゼロ化する。
`0x10001e254`の保存分類はwired / wireless / discharging。
これはOS内部の分類名で、Watchに物理USB充電があるという説明にはしない。

12温度・25残量の表示ラベルもiPhone側と一致した。
ただし、表示ラベルと生成側の厳密な端点比較は別。
全要素を配列として読めることだけで、70°C超の処理を確定しない。

### 保存済みログの再検査

90ファイルの既存コーパスを再読し、当該ヒートマップは28ファイルのWatchログで確認した。
計4,760行、170座標で、地図全体の異なる形は3通り。
Countが1 / 2 / 3の各群では、同群の別日ファイルの座標とsumが完全に一致した
（ファイル数17 / 8 / 3）。Countで割った値も3通りで、同じ集計件数どうしの変化はなかった。
28ファイルのファイル全体SHA-256は全て異なり、同じ原本を複製して数えただけではない。

これは一般的な成功率の標本ではない。またCountで割れば最新の温度履歴になるという意味でもない。
OSの保管済み分布を繰り返し集計している可能性と整合するが、原因をこれだけで断定はできない。
**このコーパスから毎日の新しい温度分布が得られたとはいえない。**

### SMC側に残った境界

新iPhoneとWatchの圧縮キー表を全復元した。2,936 + 1,469 = 4,405キーで、
元のキー検索命令を隔離環境で実行した結果と全件一致した。
BLTP、BLTV、CHSW、B1TI、B1WIの型・長さ・参照先も一致した。
しかし、これらの**起動用SMC画像の静的表にBHT0 / BHTBはなかった**。
「実行中のOSにも絶対存在しない」とする証拠ではなく、動的・別供給元を含めた生成処理は追い切れていない。

[SMCキー台帳](research/smc-key-layout-evidence-27.2.json)と
`scripts/research/inspect-smc-key-layout.py`へ復元方法を記録した。
後者はメタデータだけを読み、示されたRAMアドレスの値は読まない。
Watchの起動用SMCは27.2 / 24S118と27.2.1 / 24S132でバイト単位に一致した。
これだけで両OSのPowerlogや全ゲージが同一とはしない。

## 7. 8候補の利用判断と消せない情報欠落

| 候補 | 今回の判断 |
| --- | --- |
| 非充電時間・使用量 | 前段の生成式を維持。日をまたぐ区間を当日分へ厳密分割する情報はない |
| 高残量滞在 | 照合した10区分ゲージに限定すれば、区分・hours・累積性が説明可能。iPad4区分、未取得版29へは適用不可 |
| 遅い充電 | 16は誘導充電側の電流制限まで確認。全ビットや制御器の要求理由は別問題 |
| 時間帯別温度 | Watchの生成側を確認。1秒履歴や区間平均への変換、HHmmからの失われたUTC復元は不可 |
| 温度×残量 | ラベル・読出し・累積保管は確認。既存ログは新しい分布の証拠にならず、厳密な生成端点も未解決 |
| シャットダウン | 前段のUPO条件・時刻重複抑止を維持。Ra/DLOG/CriticalFlagsを独自の故障診断へ変換する全仕様は得ていない |
| 充電最適化 | 秒・セッション・OS累計の区別は前段通り。OS復元や将来版の保持を公開保証にはできない |
| 低電圧・セル接続 | 3ゲージの27区分・単位と、iPadの1バイト累積・飽和・保存先を確認。未照合の版へは一般化不可 |

「全機種で不明なし」に見せるために、生成側が違う形式を同じ名前でまとめたり、
失われた情報を推定値で埋めたりしない。
残った調査対象は、未取得の209200029本体、iPad4区分の生成定義、BHTの実行時生成元、
独自停止診断フラグの生成側。必要な証拠をこの単位で追跡する。

## 検証

研究用の合成データ検査は14件成功。4種のSMCアドレス圧縮、循環・範囲外・重複キーの拒否、
ゲージ版／ハッシュの不一致拒否、設定境界、既存の分類器を含む。
4,405個の実メタデータの独立照合は、この合成テストとは別に実施した。
